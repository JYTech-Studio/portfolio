## 專案概述

這個網站是我的接案作品集，也是我拿來實驗的地方。內容用 **MDX** 管理——每新增一個 `.mdx` 檔就自動多一篇案例，不用改任何程式碼。

真正想聊的是右下角那顆 🤖：一個**依我的履歷回答的 AI 分身**，而且**訪客可以自己決定要讓 Gemini 還是 Claude 來回答**。

Claude 是要付費的。開放給所有陌生訪客用付費模型，聽起來像在找死——這個案例想講的就是「**怎麼開放，又不會被燒爆**」。

## 為什麼這裡不用 RAG

我另一個作品 [RAG 知識庫問答助手](/projects/rag-assistant) 做的正是完整的檢索增強生成管線。既然做得出來，為什麼這裡不用？

因為**我的履歷只有幾千字，整份塞進 LLM 的上下文綽綽有餘**。硬套 RAG 只會多出切塊、embedding、向量檢索三道工序，換來更慢的回應、更多可能出錯的地方，以及一個「檢索沒撈到關鍵段落」的新風險——而收益是零。

技術選型的重點不是「用了多潮的東西」，是「這個問題該用什麼」。RAG 的價值在**資料大到塞不進上下文**的時候；小資料就直接塞，是更誠實的答案。

不變的是防幻覺的原則：system prompt 嚴格限定只依履歷回答，找不到就明說「這部分資料裡沒提到，建議直接 email 問本人」，絕不編造經歷。

## 開放訪客用付費模型，怎麼不會被燒爆

核心設計是**三層防護，任何一層失效都還有下一層**：

| 層 | 做法 | 擋掉什麼 |
|---|---|---|
| 1. 帳戶硬上限 | API 帳戶關閉自動儲值、設定月支出上限 | 程式全壞也不可能產生帳單——餘額歸零就整個停掉 |
| 2. 花費帳本 | 每則回答把實際 token 用量換算成美金存進資料庫，本期累計達預算就自動改用免費模型 | 正常情況下根本碰不到第 1 層 |
| 3. 速率限制 | 同一個訪客 24 小時內最多 10 則付費模型回答 | 一個人一次把整期額度刷光 |

再加上四個省錢細節：

- 用最便宜的模型（Claude Haiku）作為預設
- 單則輸出上限 800 token、只帶最近 8 則對話歷史
- **Prompt caching**：履歷那段 system prompt 每次都一樣，快取起來後 5 分鐘內的後續提問，輸入成本只算原價的一成
- 兩層預算金額**刻意錯開**：程式層先跳，帳戶上限永遠碰不到

實際估算下來，一則回答約 **0.003 美金**，1 美金大約可以撐 300 則。對一個作品集的流量來說，綽綽有餘。

## 幾個值得一提的技術細節

### 1. 花費帳本：一次查詢回答兩個問題

每次要用付費模型前，系統得知道兩件事：「這期總共花了多少？」和「這個訪客今天問了幾次？」。分兩次查資料庫等於每則訊息多一趟往返。

我把它寫成一支 PostgreSQL 函式，一次回傳兩個數字：

```sql
create or replace function chat_claude_usage(
  p_ip_hash text, p_since timestamptz, p_ip_since timestamptz
)
returns table (spent_usd numeric, ip_count bigint)
language sql stable as $$
  select
    coalesce((select sum(cost_usd) from portfolio_chat_logs
              where provider = 'claude' and created_at >= p_since), 0),
    (select count(*) from portfolio_chat_logs
     where provider = 'claude' and ip_hash = p_ip_hash
       and created_at >= p_ip_since);
$$;
```

搭配 `(provider, created_at)` 與 `(ip_hash, created_at)` 兩組索引，這支函式的成本可以忽略不計。

### 2. 超支不是報錯，是優雅降級

額度用完時，最糟的處理方式是丟一個錯誤給訪客。我的做法是**自動退回免費模型繼續回答**，並附上一句說明「這期的 Claude 體驗額度用完了，先由 Gemini 回答」，同時把前端的切換鈕鎖起來。

同樣的原則用在整條鏈路上：資料庫查詢設 2 秒逾時，Supabase 慢或掛掉時最多等 2 秒就放棄記錄——**記錄失敗絕不能影響聊天本身**。付費模型暫時限流（429 / 503）則自動重試三次。

使用者不該為了我的後端問題買單。

### 3. 速率限制要做，個資不要留

要限制「同一個人每天最多幾則」，直覺做法是把 IP 存進資料庫。但 IP 在多數隱私法規下屬於個人資料，為了一個聊天機器人的流量控制而留下一堆訪客 IP，並不划算。

所以我存的是**加鹽後的 SHA-256 雜湊**：同一個 IP 每次都算出同一個雜湊值（所以限流有效），但從雜湊反推不出原始 IP。**功能要做到，資料能不留就不留。**

### 4. 紀錄表對外完全關閉

對話紀錄表開啟了 PostgreSQL 的 **RLS（Row Level Security）**，但**刻意不建立任何存取政策**——意思是用公開金鑰的前端，對這張表既讀不到也寫不到。

所有寫入都走 server 端的 service role 金鑰（會繞過 RLS），金鑰只存在 Vercel 的環境變數裡，永遠不會出現在瀏覽器。

### 5. 讓運算和資料庫待在同一個機房

系統每則訊息會打兩次資料庫。如果 Serverless Function 跑在美東、資料庫在新加坡，每次往返都要繞半個地球。

所以我把 Vercel 的 Function Region 和 Supabase 專案**都設在新加坡**——同區之間的查詢是個位數毫秒，那兩次往返直接變成可以忽略的成本。這種設定改一次、受益永久，是很划算的優化。

## 技術架構

| 層面 | 技術 |
|------|------|
| 框架 | Next.js 16（App Router、Turbopack）+ TypeScript |
| 樣式 | Tailwind CSS v4 |
| 內容 | MDX（`next-mdx-remote` 渲染、`gray-matter` 讀 frontmatter） |
| LLM | Google Gemini（預設、免費）／ Anthropic Claude（可切換、付費） |
| 資料庫 | Supabase（PostgreSQL）——對話紀錄與花費帳本，RLS 全關 |
| 部署 | Vercel（Function Region 與資料庫同區） |

## 我從這個專案得到什麼

一般的「串 LLM API」教學到「能回答」就結束了。但真正要把 AI 功能**放到線上給不認識的人用**，後面還有一整段：成本會不會失控、被濫用怎麼辦、外部服務掛掉時使用者看到什麼、要不要留訪客的個資。

這些問題沒有一個是 AI 問題，全都是**工程問題**。而我認為那才是「能上線」和「只是能跑」的差別。
