## 專案背景

鎧福旅行社原本的報名與營運系統是一套舊版 **Express + 純 HTML** 系統，流程仰賴人工、難以維護也難以擴充。我負責把整套系統**重構為 Next.js 16 App Router + Supabase** 架構，在保留既有業務流程的前提下，將前台與後台整合進同一套現代化架構，並針對旅行社的實際營運需求(尤其是銀髮族客群)優化體驗。

這是一個**由我獨立完成**的全端專案——從前端介面、後端 API、資料庫設計、第三方整合，到部署與長期維護，整條鏈路一手包辦。

## 專案規模

這不是一個 landing page，而是一套真正在營運的商業系統：

- **前台**：首頁、行程詳情、報名人數選擇、報名表單、完成頁、客製化需求等完整流程
- **後台**：9 個主要管理模組(Dashboard、行程、報名、財務、報表、CRM、帳號、系統設定、登入)
- **API**：65 個 route file、80 個 HTTP handler
- **資料庫**：14 張資料表 + migrations(Supabase PostgreSQL)
- **維運**：24 個月維護合約，持續迭代至 v2.0.5

## 核心功能

### 前台 — 線上報名
- 多人報名(成人 / 小孩佔床 / 小孩不佔床)，不同身分別**即時計價**
- 證件資料收集與影本上傳(護照 / 台胞證 / 身分證)，護照、台胞證效期自動帶入
- 國籍採**搜尋式下拉**，支援中文名、英文名、國家代碼搜尋，顯示統一為「國旗 + 英文名 + 中文名 + 國家代碼」
- 報名確認 Email(含訂金、匯款資訊、旅行社 LINE 區塊)與報名完成頁
- 自動建立 / 更新 CRM 客戶資料

### 後台 — 營運中樞
- **行程管理**：完整 CRUD、圖片上傳、複製、排序、訂金設定、過期行程自動下架(pg_cron)
- **報名管理**：全站查單、後台手動新增報名(寬版工作流 Modal + 草稿暫存)、Excel 匯出、補發確認信
- **財務管理**：收款 / 支出 / 供應商費用、行程損益分析、月結報告、付款狀態自動連動
- **CRM**：客戶資料自動同步、標籤管理、依標籤批次群發 Email
- **報表中心**：近 12 個月銷售趨勢、行程排行、付款分佈、回購率分析(Chart.js)
- **帳號與權限**：Supabase Auth + 角色管理(Admin / SuperAdmin)，含完整守門邏輯

## 幾個值得一提的技術細節

真正決定一套系統好不好用、穩不穩的，往往是這些不顯眼卻關鍵的地方。

### 1. 台灣身分證檢核碼驗證(前後端共用)
身分證號碼不是「有 10 碼就好」——台灣身分證有固定的檢核碼演算法。我把驗證邏輯抽成一份**前後端共用的 helper**，讓前台即時驗證與後端(public API、admin API)寫入前驗證走同一份程式，確保不會因為前端被繞過而存進錯誤資料。

### 2. 前後台計價與國籍「單一真實來源」
前台旅客選的身分別與國籍，必須與後台計價、Email、Excel 匯出的規則**完全一致**。我把計價規則(小孩不佔床 = 原價 − NT$1,000、訂金 = 每人訂金 × 人數)與國籍對照表統一成單一來源，避免「前台一個價、後台另一個價」這種最容易引發客訴的問題。

### 3. 權限守門：不能刪掉「最後一位 SuperAdmin」
帳號系統最怕把自己鎖在門外。我實作了守門邏輯：**禁止停用 / 刪除 / 降權最後一位啟用中的 SuperAdmin**，並讓登入者在列表中無法對自己執行危險操作——把「系統管理員把自己誤刪」這種災難從根本擋掉。

### 4. 用資料庫保證資料正確，而非靠 application code
- 報名編號由 **DB function 原子產生**，避免高併發重號
- 付款狀態由 **DB trigger** 依實收紀錄自動重算，不靠手動更新
- 過期行程下架、rate limiting 都做在 DB / pg_cron 層，**不依賴單一 Node process**，部署在 Render 上也穩定

### 5. Next.js 16 的 Auth 時序競態
重構過程踩到一個隱晦的雷：後台登入成功後，偶發被導回登入頁。根因是 Supabase auth cookie 與 App Router client cache 的**時序競態**。解法是登入 / 登出改用 `window.location.replace` 做 full document navigation，並讓所有指向 protected 路由的連結 `prefetch={false}`，避免未登入的 redirect 被 prefetch cache 污染。

### 6. 安全機制
Supabase RLS、API 寫入欄位白名單、檔案上傳 Magic Bytes 驗證、XSS 防護(sanitize-html)、登入與公開 API 的 DB-based rate limiting、使用者可控 URL 以 `new URL()` 驗證只允許 http/https、Service Role Key 僅限伺服器端、管理員操作全程記錄(admin_logs)。

## 成果

- 報名、訂單、財務、客戶全面數位化，大幅減少人工作業與出錯
- 身分證、國籍、計價等容易出錯的環節，改由系統與資料庫層層把關
- 前後台共用邏輯 + 完整交接文件，讓長期維護不再依賴口耳相傳

## 學到的事

這個專案讓我更確信：**魔鬼藏在細節裡**。一套系統會不會出包，通常不在於主要功能，而在於檢核碼、計價一致性、權限守門、auth 時序這些不顯眼的地方——而把這些細節做對，正是專業與業餘的分界。
